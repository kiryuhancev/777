Для входа необходимы публичная конфигурация Supabase и SDK. Изолированный local cache профиля не считается авторизацией. Текущий хостинг — GitHub Pages; раздел GitLab оставлен как вариант будущего переноса.

# VAULT: Supabase и GitLab Pages

Текущий frontend — один автономный `index.html`. Игры используют прежние RNG, физику, ставки и общий `state.balance`. Инфраструктура находится в `vault/` и встроена в HTML; изменения этих файлов применяются командой `python3 tools/embed-vault.py`. Для размещения сборщик не нужен.

## Подключение

1. Создайте Supabase project. В SQL Editor выполните **весь** `supabase_schema.sql`. Скрипт допускает повторный запуск для этой версии схемы.
2. В Project Settings → API / API Keys получите Project URL и **publishable key** (`sb_publishable_…`) либо legacy **anon** key. Не используйте `service_role`, `sb_secret_…`, пароль БД или приватные ключи.
3. В `vault/config.js` заполните `VAULT_CONFIG.supabaseUrl` и `VAULT_CONFIG.supabaseAnonKey`. Затем выполните `python3 tools/embed-vault.py`. Можно редактировать соответствующий блок `VAULT CONFIG` непосредственно в HTML, но тогда обновите и исходный config перед следующим встраиванием.
4. В Authentication → Providers включите Email. Для production оставьте подтверждение email включённым. Письмо подтверждает адрес; после подтверждения вернитесь к SIGN IN. Для реальных писем настройте SMTP и проверьте доставку. Пароли не сохраняются кодом VAULT.
5. В Authentication → URL Configuration укажите Site URL: **точный URL из GitLab Deploy → Pages**, включая путь проекта, если он есть. Добавьте этот URL и его допустимые пути в Redirect URLs. Добавьте `http://localhost:8777/**` и `http://127.0.0.1:8777/**` для разработки. Не добавляйте произвольные сторонние origins.
6. Загрузите репозиторий в GitLab, включите Pages и запустите pipeline default branch. `.gitlab-ci.yml` просто копирует HTML в `public/`; backend в CI не разворачивается. Конфигурация рассчитана на современный GitLab с `pages.publish`.
7. Локально выполните `python3 -m http.server 8777` в корне репозитория. Для Auth используйте HTTP origin. Простое открытие `index.html` остаётся guest-режимом: авторизация через `file://` намеренно не подключается.
8. Создайте два тестовых аккаунта, сыграйте, обновите страницу и войдите в другом профиле браузера. В Supabase Table Editor проверьте `profiles`, `wallets`, `game_rounds`, `game_stats`, `user_settings`.

Публичный ключ не является секретом: доступ определяется JWT пользователя, RLS, grants и проверками `auth.uid()` в RPC. SDK загружается только при настроенном Supabase. При наличии account cache экран открывается сразу, затем сессия и профиль проверяются в фоне; это не вызывает возврат в лобби или сброс живого раунда. Без конфигурации или сети приложение работает локально; загрузка SDK ограничена таймаутом. При недоступном storage выводится предупреждение — гарантия восстановления требует работоспособного localStorage.

## Данные и поток

```text
Игровое действие
  → VaultRoundService.begin / VaultWalletService.applyDelta
  → единственный state.balance + явный business snapshot в localStorage
  → ограниченная очередь пользователя
  → begin_game_round / record_game_round
  → транзакция PostgreSQL: wallet + round + stats + XP + recovery
```

Настройки сохраняются с debounce 300 ms, сеть — 900 ms. Критические списания/начисления записываются локально сразу. Ни физика, ни DOM, ни таймеры, ни кадры анимации в cache не попадают. Максимум 250 событий очереди и 100 локальных завершённых раундов; полная история авторизованного пользователя остаётся в БД. Заполненная очередь блокирует новые раунды, оставляя место для завершения текущих; неотправленные денежные события не выбрасываются ради новых.

Облачный профиль — источник истины. Настройки используют timestamp и LWW. Кошелёк синхронизируется событиями, не абсолютным произвольным `UPDATE`. `revision` проверяется при начале раунда: устаревшая копия баланса вызывает конфликт, а не выбор максимального значения. Все повторы используют прежний `round_id`; проигранный сетевой ответ можно повторить без второй выплаты.

При конфликте игра блокирует новые раунды. Кнопка «Облачные данные» требует явного подтверждения отказа от неподтверждённых локальных раундов, затем загружает серверный баланс. Завершённые сервером транзакции остаются в истории. Неподтверждённые локальные результаты не считаются автоматически выигрышем. Если сервер хранит зависший started round, явное облачное восстановление закрывает его без дополнительной выплаты; до этого новый раунд той же игры не принимается.

Guest → account переносит **только настройки, ставки и последнюю игру**. Кошелёк, история и бонусы гостя не импортируются. Начальный баланс аккаунта задаётся `public.vault_configuration.starting_balance`, начальный баланс гостя — `VAULT_CONFIG.guestStartingBalance` (сейчас оба 1 000 000). Изменение SQL значения влияет на новых пользователей; существующие кошельки не сбрасываются.

Во время живого раунда или автоигры бонуса смена аккаунта недоступна, чтобы ожидающий callback не начислил результат следующему пользователю. Между спинами поставленный на паузу бонус остаётся в namespace владельца, и смена аккаунта безопасна. Выход восстанавливает отдельный гостевой cache. `TOKEN_REFRESHED` не сбрасывает игру. В браузерах с Web Locks одна вкладка на identity может изменять кошелёк; отдельные устройства защищаются серверной revision.

## Безопасные точки восстановления

| Игра | Сохраняется | После F5 во время раунда |
|---|---|---|
| Digital Derby | ставка, настройки, общий баланс; бонус между спинами: тип, размер, оставшиеся спины, прогресс, Sticky Wilds, сумма бонуса | Уже списанная ставка и начисленные каскады остаются; текущий каскад отменяется. Начатый free spin считается использованным. Бонус восстанавливается на последнем checkpoint без autoplay. Оплаченная покупка сохраняет право на бонус даже при reload до интро. |
| Poker Blitz | ставка, баланс, запись начатого/завершённого раунда | Незавершённая раздача отменяется без возврата. Карты, подсмотр и тактика не восстанавливаются. Уже завершённая выплата не повторяется. |
| Bird Siege | ставка, баланс, начисленные награды, история/статистика | Незавершённый раунд отменяется без возврата; награды за уже уничтоженных свинок сохраняются. Тела, скорости, полёт и таймеры сбрасываются. |

`started` превращается в `cancelled` с фактически уже начисленным payout. Это не бесплатная попытка и не возврат ставки. Новый оплачиваемый раунд получает новый UUID. Bonus checkpoints приходят на сервер с денежной транзакцией, а не как произвольная изменяемая настройка.

## localStorage keys

- `vault:v1:guest`: version/timestamp, гостевой wallet, preferences, безопасные checkpoints, история/статистика.
- `vault:v1:user:<UUID>`: cache конкретного аккаунта, его checkpoints и `queue` с привязанными к user ID событиями.
- `vault:v1:session`: последняя identity/profile для offline recovery; без пароля и приватных ключей.
- `vault:v1:auth` и стандартные вспомогательные ключи этого storageKey (например `vault:v1:auth-code-verifier`): Supabase SDK session/refresh tokens. Их сохраняет SDK, а не игровой код.

Это данные данного origin. Guest cache не переносится автоматически с GitHub Pages на GitLab Pages. Авторизованный пользователь входит на новом origin в тот же Supabase project и получает серверные данные. LocalStorage доступен владельцу браузера и не является защитой от читов.

Предыдущего формата persistence в исходнике не было. Повреждённый JSON, неизвестная версия, отрицательный баланс и недопустимые ставки игнорируются; transient state не мигрируется.

## Границы текущего этапа

RLS изолирует пользователей; прямые изменения wallet, XP, stats, rounds и достижений запрещены. Разрешены собственные username/avatar и настройки через контролируемый RPC. Результаты игры **пока вычисляет frontend**: аутентифицированный клиент может подделать свои bet/payout при вызове RPC. Это фундамент для demo-прогресса, не защищённый real-money backend. Следующий этап заменит содержимое Wallet/Round RPC серверной RNG/settlement проверкой; интерфейсы игр уже отделены от прямых запросов к БД.

Реальные auth/email, JWT/API permissions Supabase и GitLab pipeline требуют подключённого проекта; тестовый HTTP API не подменяет эту проверку.

## Проверки

```sh
python3 tools/embed-vault.py
python3 tools/build-site.py
node --check /tmp/digital-derby-release.js
node tools/math-tests.cjs
node tools/bird-physics-tests.cjs
# при запущенном локальном HTTP server:
python3 tools/vault-local-check.py
# настоящий SDK с тестовым HTTP API, не live Supabase:
python3 tools/vault-auth-check.py
# отдельный PostgreSQL 17 test container; детали ниже:
python3 tools/supabase-sql-tests.py
```

Auth contract test при первом запуске скачивает закреплённый SDK по HTTPS в `/tmp/vault-supabase-sdk.js`; можно указать готовый файл через `VAULT_TEST_SDK`. Production URL/key в тесте заменяются fixture-конфигурацией, все реальные API запросы блокируются. Тест использует SDK этой версии, фиктивные email/JWT и перехваченные HTTP запросы. Никаких реальных аккаунтов не создаёт.

SQL test ожидает disposable контейнер `vault-postgres-test` с PostgreSQL 17, БД `vault_test` и пользователем postgres. Создать: `docker run -d --name vault-postgres-test -e POSTGRES_PASSWORD=vault-local-test-only -e POSTGRES_DB=vault_test postgres:17-alpine`. Скрипт создаёт тестовые auth roles/users и очищает их; **не запускать против production**. Он проверяет повторное применение migration, RLS A/B, запрет прямых записей, транзакции, duplicates и stale revision.

После настройки реального Supabase обязательно проверить регистрацию/письмо, вход/выход, F5, offline/online, повтор round ID, второй browser profile и попытку получить строки B токеном A. Проверять RLS нужно через клиент с JWT пользователей, а не через SQL Editor с привилегиями владельца.
